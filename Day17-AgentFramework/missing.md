# Day 17 — Agent Framework: Missing Pieces & Enhancement Opportunities

_Analysis date: 2026-08-04_

1. **Typos in the agent's `Instructions` string leak into every response** — The persona text contains three literal typos: `"bets destinations"` (should be "best destinations"), `"Alwasy provide"` (should be "Always provide"), and no space between the first two concatenated strings, producing `"...travel planner.Your goal..."`. Since `Instructions` is sent verbatim to the model as part of the system prompt, these are not just cosmetic — they're now part of the LLM-facing prompt engineering. A follow-up revision should fix the string (and this is a good moment to teach students that persona text quality directly affects a production agent's behavior).
2. **No error handling around `InvokeAsync`** — If the Gemini call fails (rate limit, network blip, invalid key), the `await foreach` loop throws unhandled and crashes the whole console session, losing the entire conversation. Wrapping the invocation in a `try/catch` — and deciding whether to retry, skip the turn, or exit gracefully — would be a natural addition, especially since this is meant to be an interactive, long-running chatbot.
3. **No cancellation token support in an interactive loop** — The `while(true)` loop blocks on `Console.ReadLine()` and then on the agent's async stream with no `CancellationToken` anywhere, so there's no way to interrupt a hung request except killing the process. Introducing a token (e.g., tied to Ctrl+C) would be a good production-readiness addition given how central "the loop runs forever until the user types exit" is to this lesson.
4. **Fixed temperature and model with no discoverability for students to tune them** — `Temperature = 0.5` and `"gemini-2.5-flash"` are hard-coded inline in the agent's `Arguments`/kernel setup, with no comment explaining why 0.5 was chosen for a travel-planning persona (as opposed to, say, the 0.0 used for factual QA in Day 14). A short comment tying the temperature choice back to the "creative vs. deterministic" lesson from Day 14 would reinforce that concept rather than silently repeating a different value.
5. **No `[KernelFunction]` tools attached to this agent, despite `ChatCompletionAgent` supporting them** — This lesson only exercises the agent's conversational/persona capability, not its ability to call plugins (which `ChatCompletionAgent` fully supports via its `Kernel` property, as shown when tools appear in later lessons). A brief callout — or an optional follow-up exercise — showing that the exact same `TimePlugin`/`WeatherPlugin` from Day 15 could be attached to this `travelAgent` would help students see that Agent Framework agents are a strict superset of the raw chat-service pattern, not a separate, less-capable one.
6. **No persistence of conversation across runs** — Like most lessons in this course, the `ChatHistory` lives only in memory and is lost the moment the program exits; there's no save/load of a prior conversation. Given this is meant to model an "assistant" a user might return to, even a simple JSON-file save/load on exit would be a valuable, low-effort addition.
7. **`message.Message.AuthorName` may print `null`/empty rather than "TravelAssistant" without explicit wiring** — The code assumes `message.Message.AuthorName` will resolve to the agent's `Name` property, but this depends on the Agent Framework populating `AuthorName` correctly on returned `ChatMessageContent`; there's no fallback (e.g. `?? travelAgent.Name`) if it doesn't. Worth a defensive `??` and a short note to students about not assuming metadata fields are always populated.
