# Day 4 — The Calculator: Missing Pieces & Enhancement Opportunities

_Analysis date: 2026-08-04_

1. **No handling of divide-by-zero or invalid arithmetic** — `Divide` performs plain `number1 / number2` with no guard. Since `double` division by zero produces `Infinity`/`NaN` rather than throwing, the model would receive a non-numeric-looking result with no explanation and could hallucinate an explanation for it. This is a natural and low-effort place to introduce input validation inside a `[KernelFunction]` — e.g., throwing a descriptive exception that Semantic Kernel can surface back to the model as a tool error.
2. **No error handling around the tool-calling loop itself** — `InvokePromptAsync` is unguarded, and there's no handling for the case where the model requests a malformed tool call, or where Gemini's API call fails mid-reasoning-chain (which is more likely here than in earlier lessons, since this call can involve several round trips). A future revision could show what a caught exception looks like specifically in a multi-step tool-calling scenario, since debugging a failed step in a chain is a different experience than debugging a single failed call.
3. **No plugin unit tests** — `MathPlugin` is a plain, easily-testable C# class (its methods have no dependency on the Kernel or AI at all), yet the lesson never demonstrates testing it directly with something like xUnit/NUnit. This is a significant missed opportunity: it's the first lesson with genuinely testable native code, and showing "you can and should unit-test your plugins independent of the AI" would be valuable for a 200-level course that presumably wants to instill good engineering habits alongside AI concepts.
4. **No limit on the number of tool-call round-trips** — `AutoInvokeKernelFunctions` allows the model to keep calling tools with no configured maximum step count. Semantic Kernel exposes a `MaximumAutoInvokeAttempts` setting on some behaviors; if the model got into a bad reasoning loop it could burn many API calls before terminating. Mentioning or configuring this bound would be a good production-readiness note.
5. **No logging/observability beyond ad hoc Console.WriteLine** — The `[NATIVE CODE EXECUTION]` print statements inside the plugin methods are a nice teaching aid for visualizing tool calls, but they're just raw console output rather than structured logging (e.g., via `ILogger<MathPlugin>`), and there's no way to disable them in a non-demo context. A follow-up could show injecting `ILogger` into the plugin constructor as the "real" way to get this visibility.
6. **Plugin has no constructor / is stateless by coincidence, not design** — `MathPlugin` happens to have no fields, so `AddFromType<MathPlugin>` works via a default-constructed instance. The lesson doesn't call out that plugins needing dependencies (e.g., an `HttpClient`, a config object) would need `AddFromObject` instead, or DI registration — a concept Day 6's `FileSystemPlugin` actually needs (it uses `AddFromObject`). Contrasting the two approaches side-by-side would reinforce when each is appropriate.
7. **No negative/adversarial word problem shown** — The lesson always demonstrates the "happy path" chain of tool calls succeeding. Showing what happens if the prompt is ambiguous (e.g., a problem solvable with or without tools) would teach students that `AutoInvokeKernelFunctions` doesn't force tool use — it only permits it — and the model can still choose to answer from its own reasoning when it believes a tool isn't needed.
