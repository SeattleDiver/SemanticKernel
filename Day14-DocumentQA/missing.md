# Day 14 — Document QA: Missing Pieces & Enhancement Opportunities

_Analysis date: 2026-08-04_

1. **No real file loading, despite the code commenting on it** — The comment on line 29 (`// In a real scenario, use File.ReadAllTextAsync("huge_document.txt")`) points at the realistic use case, but the code only ever calls `GenerateSampleTechnicalDoc()`. A follow-up revision could actually load a `.txt`/`.md` file from disk (with a `try/catch` around missing-file cases), so students see the context-window-size problem for real instead of being told about it in a comment.
2. **No context-window size guardrail or warning** — Because this lesson's whole teaching point is "we're stuffing the entire document into context," there is no code that measures the document's token/character count or warns the student when it would exceed a real model's context window. A simple `longDocument.Length` check with a printed warning ("this document is N characters; Gemini's context window is X") would make the RAG-vs-stuffing contrast in the header comment concrete rather than just asserted.
3. **No conversation memory across questions, and it's not called out to the student** — Each question is answered via a fresh `InvokePromptAsync` call with no `ChatHistory`, so a student asking "what about the previous one" gets a confused answer with no explanation of why. The walkthrough should (and now does, in the produced lesson doc) explicitly flag this, but the code itself gives no runtime signal — a follow-up revision could print a one-line reminder ("Note: each question is answered independently; there is no memory between turns") right in the console banner.
4. **Result printed via implicit `ToString()`, not `.GetValue<string>()`** — `Console.WriteLine($"\nAI: {result}\n")` relies on `FunctionResult.ToString()` doing the right thing. It works, but it's an implicit conversion the student is never shown; a small aside or an explicit `result.GetValue<string>()` would teach the actual `FunctionResult` API surface rather than relying on operator magic.
5. **No error handling around the Gemini call** — `InvokePromptAsync` can throw (network failure, rate limiting, malformed response) and none of that is caught, so any transient error crashes the whole console loop and the student loses their place. Even a minimal `try/catch` that prints the error and continues the loop would make this resilient enough to demo live without a crash derailing class.
6. **No `[KernelFunction]`/plugin structure to reinforce reusability** — `GenerateSampleTechnicalDoc` and the QA logic are just static helper methods baked into `Program.cs`; nothing here is packaged as a reusable Semantic Kernel plugin. Since later lessons (Day 15 onward) rely heavily on `[KernelFunction]`-decorated plugin classes, a forward-looking revision could show the "document lookup" as a plugin function even in this pre-plugin lesson, to make the on-ramp into Day 15 smoother.
7. **Hard-coded document topic prevents easy re-use for a different demo** — The manual, prompt persona ("Quantum-X"), and instructions are all hard-coded strings inside `Main`. Extracting the persona/document into separate constants or a config file would let instructors swap in a different sample document for variety without editing the control flow.
