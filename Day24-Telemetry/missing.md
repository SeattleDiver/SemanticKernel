# Day 24 — Telemetry & Observability: Missing Pieces & Enhancement Opportunities

_Analysis date: 2026-08-04_

1. **No metrics or logging pipeline, only tracing** — the lesson wires up `TracerProviderBuilder` for traces exclusively; OpenTelemetry's other two pillars (metrics — e.g., token counts, request counts — and structured logs) are never mentioned or configured, even though `Microsoft.SemanticKernel` also emits meter-based instrumentation. Since the course frames this as "Telemetry & Observability" broadly, a brief `MeterProviderBuilder` example (even just counting total Gemini calls) would round out the three-pillars story instead of only showing traces.
2. **Plugin registered without an explicit name, unlike other lessons' plugins** — `builder.Plugins.AddFromType<SlowWeatherPlugin>()` omits the plugin-name argument that Day 20-22's plugin registrations consistently use (e.g., `AddFromType<SecureDatabasePlugin>("Database")`). This means the plugin's default name is derived from the class name, and the resulting trace `DisplayName` for the tool span will read differently than students might expect from prior lessons' naming conventions. Passing an explicit name (e.g., `"Weather"`) would keep this lesson's telemetry labels consistent with the course's established plugin-naming pattern and make trace output easier to read.
3. **No exception/error-path telemetry demonstrated** — the entire demo is a single happy-path request; no code path shows what a trace looks like when the plugin throws, the model call times out, or the API key is invalid. Since production observability is often needed most during failures, a second demonstration run with an artificial exception (e.g., `SlowWeatherPlugin` throwing for a specific city) showing the resulting error span/status would make the observability story materially more complete.
4. **No custom spans or business-level telemetry, only what Semantic Kernel emits automatically** — `AddSource("Microsoft.SemanticKernel*")` captures only SK's built-in activities; the lesson never shows creating your own `ActivitySource`/`Activity` to add application-specific context (e.g., a span wrapping the whole "answer this user's weather question" business operation, or custom tags like a user ID or session ID). Given later real-world systems need to correlate SK's internal spans with your own application-level spans, at least one example of `new ActivitySource("MyApp").StartActivity(...)` around the `InvokePromptAsync` call would teach a skill students will need immediately after this course.
5. **Console exporter output is unstructured and hard to parse, with no guidance on reading it** — the walkthrough correctly notes the console output will be "highly verbose," but the code does nothing to make the printed activity data more approachable (no filtering to just `DisplayName`/`Duration`, no color-coding, no summary at the end). A short custom `Console.WriteLine` summary after `ForceFlush()` — e.g., iterating captured activities and printing a one-line-per-span table — would make the demonstration's payoff much clearer for students seeing OTel output for the first time.
6. **No mention of sampling** — every single activity is captured and exported with no sampling strategy discussed (OTel's default is "always on" for a manually built `TracerProviderBuilder` with no sampler configured, which is fine for a one-shot demo but would be a real production cost/volume concern at scale). Even a one-sentence mention of `TraceIdRatioBasedSampler` for high-traffic scenarios would responsibly frame this demo as "development mode" rather than something to copy verbatim into production.
7. **API key and model name still hardcoded with no configuration layer** — consistent with other lessons in this series, `"gemini-2.5-flash"` and the `GEMINI_API_KEY` environment-variable pattern are hardcoded directly in `Main`. Since this is described as "the series capstone," it would be a natural point to introduce `Microsoft.Extensions.Configuration` (appsettings.json + environment variable layering) as the more production-realistic way to supply both the model name and secrets, tying together a configuration lesson with the observability lesson.
8. **No correlation shown between the OTel trace and application-level console logs** — `Console.WriteLine` statements (like "Starting observability session...") and the OTel-captured activity output are interleaved in the terminal with no shared trace/correlation ID linking a given user-facing log line to the spans it produced. Demonstrating how to read `Activity.Current?.TraceId` inside application code (and printing it alongside the "User:" and "Final AI Output:" lines) would show students how to stitch their own log lines to the distributed trace, a very common real-world observability need.
