# Day 15 — Multi-Tool Agent: Missing Pieces & Enhancement Opportunities

_Analysis date: 2026-08-04_

1. **No way to confirm the model actually used both tools versus one** — The lesson's entire pedagogical point is "the model selects among tools," but the only evidence offered is the `[EXECUTING TOOL]` console lines. There's no assertion, count, or summary print (e.g., "Tools invoked this turn: GetLocalTime, GetWeather") confirming both fired for the compound question. A future revision could track invocation counts in each plugin (similar to `ResearchPlugin._stepCount` in Day 16) and print a small "tool usage report" after the final answer so the selection behavior is provable, not just visually inferred.
2. **Hard-coded single question, no interactive loop** — Unlike Day 1's chatbot or Day 14's QA loop, this program asks exactly one hard-coded question and exits. Students can't experiment with different phrasings to see how tool selection changes. Wrapping the request in a `while(true)` / `Console.ReadLine()` loop (as later lessons do) would let students test edge cases live, e.g. a question that needs only one tool, or neither.
3. **`WeatherPlugin.GetWeather` has fake, hard-coded logic with no input validation** — The "weather" is literally `city.Contains("London") ? ... : "22°C and Sunny"`, so any city other than London gets the same canned answer, and a null/empty city isn't guarded against (`city.Contains` would throw on a null `city`, though the framework is unlikely to pass null). Since this is a teaching stub this is acceptable, but a follow-up could call a real weather API (or a slightly richer mock with 3-4 cities) to make the "tool actually does something useful" idea more convincing.
4. **No error handling around the model call or tool execution** — If Gemini's API call fails, or if a tool method itself throws, nothing here catches it — the whole console app crashes. Given that auto-invocation runs multiple round trips under the hood (initial request, tool results, follow-up request), there are more failure points here than in a single-call lesson, making this a good place to introduce a `try/catch` around `InvokePromptAsync`.
5. **No cancellation token or timeout support** — `Main` is `async Task` with no `CancellationToken` passed anywhere, so a hung network call to Gemini (or an infinite/slow tool) has no way to be aborted. Introducing a `CancellationTokenSource` with a timeout would be a natural, low-effort addition given this lesson already awaits an async call.
6. **No limit on how many auto-invoked tool calls the model can make** — `AutoInvokeKernelFunctions` will keep calling tools until the model stops requesting them, but there is no `MaximumAutoInvokeAttempts` (or equivalent safety cap) configured on the execution settings. For a two-tool demo this is low risk, but it's worth calling out to students now, since Day 16 will show manually why an iteration cap matters once loops get more complex.
7. **Plugin classes are stateless and print directly to `Console`, with no separation of concerns** — Both plugins call `Console.WriteLine` directly inside business logic, coupling the "tool" to the console UI. A more production-minded version would return data only and let the caller (or a logging abstraction) decide how/where to report tool invocations — worth flagging since later lessons keep this same pattern.
