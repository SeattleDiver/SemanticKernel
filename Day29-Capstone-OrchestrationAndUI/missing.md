# Day 29 — Capstone Implementation (Orchestration & UI): Missing Pieces & Enhancement Opportunities

_Analysis date: 2026-08-04_

1. **Malformed interpolated strings hide real Reviewer output** — In `ReviewerAgent.cs`, the rejection branch logs `Console.WriteLine("  [REVIEWER] Task {task.Id} rejected. Reason: {review}");` as a plain string literal (missing the `$` prefix), so at runtime it prints the literal text `{task.Id}` and `{review}` instead of the actual task ID and rejection reason. Likewise, the rejection path overwrites `task.Description = $"[REVIEWER FEEDBACK] {review}"` instead of appending, so the original task description is lost on rework — the Developer's retry prompt no longer contains the original requirement, only the critique. A future revision should fix both: use `$"..."` for the log line, and change `=` to `+=` (matching the docx reference's original intent) so feedback augments rather than replaces the task description.
2. **No safeguard against infinite Planner task growth** — `PlannerAgent` runs once per orchestration cycle and calls `CreateTask` via auto-invoked tool calling. Nothing stops the Planner from being re-invoked every cycle and adding two *more* tasks each time (the plugin has no check for "have I already planned this project?"). In practice the current happy-path prompt causes this to mostly go unnoticed, but it is a latent bug: a slow-to-converge Reviewer loop would also cause the task list to keep growing every cycle instead of just being reworked. A follow-up lesson could have the Planner check `state.Tasks.Any()` before creating new tasks, or move planning outside the per-cycle loop entirely.
3. **No cancellation or timeout support** — `ExecuteAsync(ProjectState state)` on `IProjectAgent` takes no `CancellationToken`, and none of the `InvokePromptAsync` calls pass one. In a console demo this is harmless, but it means a hung Gemini call blocks the whole orchestration cycle indefinitely with no way for the caller to abort. Adding a `CancellationToken` parameter threaded through `IProjectAgent.ExecuteAsync` and the orchestrator's loop would be a natural next step, especially since Day 30 reuses this exact code inside a web request pipeline where hung calls are far more costly.
4. **No retry/resilience around LLM calls** — every agent (`GoalRefinerAgent`, `PlannerAgent`, `DeveloperAgent`, `ReviewerAgent`) makes a bare `await kernel.InvokePromptAsync(...)` call with no try/catch, no retry-on-transient-failure, and no fallback if the Gemini API returns an error or rate-limits the request. A single network hiccup during the demo will throw an unhandled exception and crash the console app mid-cycle. Wrapping these calls with a simple retry policy (or at least a try/catch that logs and marks the task failed rather than crashing) would make this closer to something students could rely on outside a live demo.
5. **`ProjectTask.Result` is not nullable-annotated correctly** — the project has `<Nullable>enable</Nullable>` in the csproj, yet `ProjectTask.Result` is declared as `public string Result { get; set; }` with no default value and no `?`. This should produce a nullable-reference-type warning (CS8618) on build. A cleanup pass should either default it to `string.Empty` (matching the other string properties in the same class) or explicitly mark it `string?` since it is genuinely unset until the Developer runs.
6. **No persistence of `ProjectState` across runs** — the entire multi-agent conversation, plan, and generated code exist only in memory for the duration of `Main` and are printed to the console once at the end. There's no way to save a run, resume a rejected review cycle later, or compare multiple runs. Even a simple `File.WriteAllText` of the final `ProjectState` as JSON at the end of `Program.cs` would let students inspect results after the console window closes and would set up nicely for Day 30's transition to returning `ProjectState` as an HTTP JSON response.
7. **No unit tests for the Reviewer's approve/reject branching or the orchestrator's convergence logic** — the course has reached a point where the control flow (cycle limits, state mutation, convergence via `IsFullyCompleted`) is complex enough to be worth testing in isolation from the live LLM. A lightweight fake `IProjectAgent` used in a unit test could exercise `ProjectOrchestrator.RunProjectAsync`'s cycle-counting and early-exit behavior without any network calls, and would double as a teaching moment on testing agentic code.
8. **Typos in user-facing/log strings** — several strings shipped in this lesson contain typos that leak into console output and LLM prompts: `"techincal implementation tasks"`, `"Low temperatore for deterministic planning"`, `"CreateTAsk autonomously"` (comment), `"Deos the code completely satisfy the task?"` (sent verbatim to the Reviewer LLM), `"a string QA Reviewer"` (should be "strict"), and `"Maximum cycles reached without full cmpletion"`. None of these break functionality, but `"Deos"` and `"a string QA Reviewer"` are sent as part of the actual prompt text to Gemini, which is worth cleaning up so students see a professional-quality prompt.
