# Day 6 — The File Manager: Missing Pieces & Enhancement Opportunities

_Analysis date: 2026-08-04_

1. **Sandboxing is directory-scoped only, not path-traversal-safe** — `FileSystemPlugin` restricts operations to `Directory.GetCurrentDirectory()`, but `Path.Combine(_currentDirectory, fileName)` does not validate `fileName` afterward. If the model (or a prompt-injected instruction inside a file it reads) supplied something like `../../secrets.txt` or an absolute path, `Path.Combine` would happily escape the intended sandbox. Since this lesson's explicit teaching point is AI sandboxing/security, this is the single most important gap: a real hardening step would resolve the combined path with `Path.GetFullPath` and verify it still starts with `_currentDirectory` before allowing the operation, and the lesson should say so.
2. **No error handling around the AI call or the tool-chaining loop** — As in every previous lesson, `InvokePromptAsync` is unguarded. This lesson is a stronger case for it than most: a multi-step chain (list → read → write) has more failure surface than a single call, and any failure mid-chain (e.g., the model errors out after `ListFiles` but before `WriteFile`) currently just crashes with no partial-progress visibility.
3. **WriteFile has no overwrite protection or confirmation** — `WriteFileAsync` unconditionally overwrites any existing file with the given name via `File.WriteAllTextAsync`, with no check for whether `error_summary.txt` (or any other target name the model chooses) already exists and contains something the user cares about. For a plugin capable of destructive side effects, this is a real production concern worth calling out — a safer version might refuse to overwrite, or require an explicit `overwrite: true` parameter.
4. **No DeleteFile or path-listing depth control, but also no rate/operation limiting** — The plugin only supports list/read/write, which is appropriately minimal, but there's also no limit on how many times the AI can invoke these tools in one run (no analog to `MaximumAutoInvokeAttempts`). A model that got stuck in a loop calling `ReadFile` repeatedly would not be stopped by anything in this code.
5. **Unused/leftover using directive** — `using System.Security.Cryptography.X509Certificates;` at the top of `Program.cs` is not used anywhere in the file. It's harmless but suggests copy-paste residue from another file; a cleanup pass should remove it so students don't wonder why a certificates namespace is imported into a file-manager demo.
6. **No handling of binary or very large files** — `ReadFileAsync`/`WriteFileAsync` assume UTF-8 text via `File.ReadAllTextAsync`/`WriteAllTextAsync`, with no size limit and no handling of binary files (which would throw or produce garbled text when "read" as a string). Given the model chooses which file to read based only on `ListFiles`' output, nothing stops it from trying to read a large binary file if one happened to exist in the directory — worth at least a defensive check and a clear error message.
7. **No logging distinguishing plugin-execution output from AI narration** — `[PLUGIN EXECUTING]` console lines are a nice visual aid, but they're mixed into the same `Console.WriteLine` stream as the AI's final report and the verification output, with no timestamps, structured logging, or way to filter one from the other. Introducing `ILogger` here (as also noted for Day 4) would be a natural, cumulative through-line for a "how do real systems observe agent behavior" thread across the course.
8. **No test coverage for the plugin's file operations** — Like `MathPlugin` in Day 4, `FileSystemPlugin`'s methods are pure, testable C# (aside from real disk I/O) but the lesson never demonstrates testing them — e.g., with a temp-directory-based unit test verifying the sandbox actually holds, or verifying `ReadFile` returns the documented error string for a missing file. Given the security emphasis of this specific lesson, a unit test proving the sandbox can't be escaped would reinforce the lesson's own stated goal.
