# Day 28 — Capstone Implementation (Plugins & Single Agents): Missing Pieces & Enhancement Opportunities

_Analysis date: 2026-08-04_

1. **`DeveloperAgent._baseKernel` is a public field, breaking the encapsulation pattern used everywhere else** — Every other agent (`GoalRefinerAgent`, `PlannerAgent`) declares its kernel reference `private readonly`. `DeveloperAgent` declares `public readonly Kernel _baseKernel;` — a visible inconsistency that lets any external caller reach in and grab (or worse, someone extending the class could reassign a mutable version of) the agent's kernel directly, bypassing the `IProjectAgent` contract. This should be `private readonly` to match its siblings; it's a good one-line fix-and-discuss moment for a course revision on encapsulation.

2. **No guardrail on how many tasks the Planner can create** — The Planner's prompt asks the model to create "exactly 2" tasks via `CreateTask`, but nothing in code enforces or even checks that count. Because `ToolCallBehavior.AutoInvokeKernelFunctions` lets the model call the tool as many times as it wants, a model that doesn't follow instructions precisely could create 0, 1, or 10 tasks, and the Developer stage would silently process however many exist — with no cost/complexity ceiling and no validation step after planning that checks `state.Tasks.Count` against an expected range.

3. **Tasks assigned to a role other than "Developer" are silently dropped** — `ProjectManagementPlugin.CreateTask`'s `assignedTo` parameter description explicitly allows `'Developer'`, `'Reviewer'`, or `'Tester'`, but only `DeveloperAgent` exists to consume tasks in this lesson. If the Planner's LLM ever assigns a task to `"Reviewer"` or `"Tester"` (which its own tool description invites it to do), that task is added to `state.Tasks` but no agent will ever pick it up, complete it, or even report that it was orphaned — it just sits there permanently `IsCompleted = false` with no diagnostic message. A revision could either narrow the plugin's description to only the roles that have an implementing agent, or add an explicit "unassignable task" warning when the final state is printed.

4. **No error handling around either `InvokePromptAsync` call in Planner or Developer** — Neither `PlannerAgent.ExecuteAsync` nor `DeveloperAgent.ExecuteAsync` has a try/catch, timeout, or retry around its model call. Since these two calls now sit in the middle of a three-stage pipeline (Refiner → Planner → Developer), a single transient failure on either call aborts the whole run and leaves `ProjectState` in a partially-completed, unrecoverable state with no context printed about which stage failed or why.

5. **Tool implementation does console I/O directly, hurting testability** — `ProjectManagementPlugin.CreateTask` calls `Console.WriteLine` directly inside the method the LLM invokes. This couples the plugin's core logic (mutating `ProjectState`) to a specific console-based UI, making it hard to unit-test the plugin in isolation (e.g., in a future automated test using a fake `ProjectState`) without capturing or suppressing console output. A cleaner design would separate the state mutation from the "tool executed" notification, e.g. via an event, callback, or logger abstraction.

6. **No validation of `Description`/`assignedTo` arguments in `CreateTask`** — The tool blindly accepts whatever strings the model supplies — an empty `description`, or an `assignedTo` value that doesn't match any known role — with no validation or normalization (e.g., trimming, case-insensitive role matching). Given that `DeveloperAgent` compares `t.AssignedTo == this.Name` with an exact, case-sensitive string match, a model that returns `"developer"` (lowercase) instead of `"Developer"` would silently fail to match and the task would never be picked up — a subtle and hard-to-debug failure mode worth guarding against or at least explaining.

7. **No unit tests for the plugin or agents** — `ProjectManagementPlugin.CreateTask` is pure, deterministic C# logic (given a `ProjectState`, it appends a task and returns a string) and would be trivial to unit test without any LLM involvement, but no test project exists. Likewise, neither `PlannerAgent` nor `DeveloperAgent` can be tested without a live Gemini call, since both take a concrete `Kernel` rather than an injectable abstraction — a missed opportunity to demonstrate testable agent design in a lesson that's explicitly about production-shaped multi-agent architecture.

8. **Minor: unused `using` directives in `PlannerAgent.cs`** — `System`, `System.Collections.Generic`, and `System.Text` are imported but never used in the file, a small bit of cleanup a polished reference implementation should remove.
