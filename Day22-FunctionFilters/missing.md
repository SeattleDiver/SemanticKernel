# Day 22 — Function Filters: Missing Pieces & Enhancement Opportunities

_Analysis date: 2026-08-04_

1. **PromptLoggingFilter has a console formatting bug that undercuts its own demo** — `Console.Write("\n[PROMPT LOGGER] Intercepted payload headed to Gemini:")` uses `Write` (no newline) immediately followed by `Console.WriteLine(context.RenderedPrompt)`, so the rendered prompt is printed directly after the colon with no line break or visual separator (e.g. `...headed to Gemini:Can you look up the current balance...`). This is a small but very visible bug for a lesson whose entire purpose is producing readable observability output; switching the first line to `WriteLine` and adding a separator (as the reference material's own sample output implies) would fix it.
2. **AuditFunctionFilter logs less detail on entry than on exit** — the pre-execution log line only prints `context.Function.PluginName` ("AI requested tool execution: Database"), while the post-execution line prints `context.Function.Name` ("Finished GetCustomerBalance..."). A reader has to mentally stitch these together to know which specific function started. Logging `{context.Function.PluginName}.{context.Function.Name}` consistently on both lines would make the audit trail actually readable end-to-end, which matters a lot for a filter explicitly framed as an audit/security log.
3. **No actual policy enforcement demonstrated in AuditFunctionFilter** — the filter's comment says "you could cancel the execution here," but the demo never does it. Since Day 22's stated real-world motivation includes "granular security gates to prevent an LLM from calling sensitive functions," the lesson would be far more convincing with a second, small example filter that actually blocks a call (e.g., reject any `customerId` matching a denylist, or reject calls outside business hours) so students see `next()` genuinely skipped, not just described in a comment.
4. **SecureDatabasePlugin's returned string vs. its own description mismatch** — the method is decorated `[Description("Retrieves the account balance for a specific customer ID.")]` but returns a bare `"$5,240"` with no mention of the customer ID, while a fuller sentence (`"Customer {customerId} has an active balance of $5,240"`) is left commented out directly above the active line. This is exactly the kind of inconsistency that can degrade a model's ability to correctly attribute a tool result in a multi-call conversation; removing the dead commented-out line and deciding deliberately which format to return would tighten the example.
5. **No PII redaction example despite it being the flagship use case** — the lesson's own stated motivation for `IPromptRenderFilter` is "mask Personally Identifiable Information (PII) before it leaves your servers," but `PromptLoggingFilter` only logs the prompt; it never demonstrates modifying `context.RenderedPrompt` before `next()` (or after) to redact anything. Since this is the headline justification for the filter's existence, adding a second filter (or extending this one) that actually masks a fake PII pattern (e.g., an account number) would close the gap between the stated goal and the code.
6. **No error handling if the plugin throws inside the filter chain** — neither filter has a try/catch around `await next(context)`. If `GetBalanceAsync` ever threw (a real database timeout, for instance), the exception would propagate up through both filters uncaught, and the `sw.Stop()` / post-execution logging in `AuditFunctionFilter` would never run — so the audit trail would silently lose the failure. A `try/finally` around `next(context)` that always logs duration (success or failure) would make the audit filter production-realistic.
7. **Filters are process-wide singletons with no per-request scoping or ordering control** — both filters are registered as `AddSingleton` with no discussion of filter execution order when multiple filters of the same type are registered, or of using `Kernel.FunctionInvocationFilters`/`PromptRenderFilters` collections directly for per-kernel-instance filters instead of global DI registration. A brief mention of ordering semantics (filters run in registration order) would round out the "middleware" mental model the lesson is building.
8. **No unit test or way to verify filter behavior without live API calls** — because both filters only manifest their behavior via console output during a live Gemini call, there's no way for a student to verify filter logic (e.g., that AuditFunctionFilter correctly measures duration or that a hypothetical blocking filter actually blocks) without burning API quota. A future revision could add a fake `IChatCompletionService`/mock kernel so filter behavior is testable in isolation.
