# Day 21 — Semantic Router: Missing Pieces & Enhancement Opportunities

_Analysis date: 2026-08-04_

1. **No error handling around JSON deserialization or malformed router output** — `SemanticRouter.RouteAsync` calls `JsonSerializer.Deserialize<RouteDecision>(response.Content ?? "{}")` with no try/catch. If Gemini ever returns malformed JSON (truncated output, an unexpected field, a non-JSON apology string despite `ResponseMimeType`), `JsonException` propagates uncaught and crashes the whole console loop. A future revision should wrap this in a try/catch that falls back to a `GENERAL` route, matching the defensive spirit already shown by the `?? new RouteDecision { Intent = "GENERAL" }` fallback for the null case.
2. **`decision.Intent.ToUpper()` will NullReferenceException if Intent is ever missing** — `RouteDecision.Intent` defaults to `string.Empty` via its property initializer, so this specific case is safe, but there is no defensive check that `Intent` is one of the three expected values before the `switch`. An unrecognized string (e.g., the model outputs `"BILLING "` with a trailing space, or a lowercase variant not covered by `ToUpper()`) silently falls into `default` — worth calling out explicitly to students as the reason the switch has a default case at all.
3. **No retry/timeout policy on any of the three Gemini calls** — the router call, `TechSupportAgent.HandleAsync`, and `BillingAgent.HandleAsync` all await network calls with zero resilience (no retry-on-429, no timeout, no circuit breaker). Given this lesson is explicitly about production-scale routing architecture, a brief mention or wrapper (e.g., `Polly`) demonstrating a retry around the router call specifically would tie resilience concepts back to a lesson about scaling to "dozens of tools."
4. **Plugin parameter description is a copy-paste bug** — `BillingAgent.GetBalance`'s parameter is decorated `[Description("No account ID")]` (should almost certainly read "The account ID"). Since `[Description]` attributes are what the LLM reads to decide how to call a tool, an incorrect description here is a good real-world example of a subtle plugin-authoring bug that silently degrades tool-calling accuracy — worth fixing and flagging to students as a cautionary example.
5. **No conversation memory between turns** — each call to `techAgent.HandleAsync(input)` / `billingAgent.HandleAsync(input)` builds a brand-new `KernelArguments`/prompt with no `ChatHistory`, so the specialist agents have no memory of earlier turns in the same session. A user who says "reset my password" and then "actually, for user bob" gets no continuity. Given Day 20 already taught `ChatHistory`, a natural enhancement is giving each specialist its own persistent history scoped to its isolated kernel.
6. **Router miscategorization is unrecoverable within a turn** — if the router misclassifies a request (e.g., calls a billing question "GENERAL"), there is no mechanism for the specialist or the user to say "wrong, re-route this" — the turn just answers wrong and moves on. A revision could add a lightweight confidence threshold (e.g., route to a clarifying question if reasoning is weak) or let a specialist bounce a request back to the router if it determines it received the wrong intent.
7. **Hardcoded mock data with no real backing store** — `ResetPassword` and `GetBalance` are pure string-formatting stubs with no persistence, validation of `username`/`accountId` format, or simulated failure paths (e.g., unknown account). Since Day 22/23 introduce more production concerns, this lesson could at least validate that `accountId`/`username` is non-empty before "processing," to model basic input validation on tool parameters.
8. **No `[Description]` on the class-level plugin registration and no logging of the routing decision** — the router's `Reasoning` string is printed to console but never persisted or logged anywhere durable; in a real system, capturing router decisions for later analysis (to catch systematic misclassification patterns) is a common production need worth at least mentioning.
